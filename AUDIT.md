# План тотальной проверки инструмента

Что здесь: полный перечень проверок корректности — от сбора выдач до строки на экране.
Каждая проверка сформулирована так, чтобы её можно было выполнить и получить ответ
«прошла / не прошла», а не впечатление. Статусы: ✅ закрыта (и чем), ⏳ в плане,
🔒 ждёт доступов.

## Принципы

Выведены из багов, которые реально находились в этом инструменте, — каждый принцип
оплачен конкретной ошибкой:

1. **Проверять по выдаче, а не по эху запроса.** Отправленный параметр говорит, что мы
   попросили; верить можно только тому, что вернулось (фильтр оператора считаем по доле
   своих строк; параметры сверяем по датам/ночам из самих предложений).
2. **Контрольная проба с заведомым ответом.** Прежде чем верить нулю — убедиться, что
   тем же способом находится то, что точно есть (проба `hotels=<id>` показала ноль по
   Atlantis только после того, как контрольный отель вернулся).
3. **«Не нашли» ≠ «нет».** Недочитанная страница, упавший запрос и пустой ответ — три
   разных исхода, и смешение любого из них с «нет» порождает фантомные находки
   (пагинация «отелей», незавершённый поиск шлюза).
4. **Молчание честнее догадки.** Не удалось сверить номер/питание/словарь — пишем «не
   сверено», а не подставляем правдоподобное.
5. **Одинаковые единицы во всех счётчиках.** Каждое число на экране обязано сходиться с
   числом в базе тем же запросом (см. «Двойную бухгалтерию» внизу).
6. **После каждого запуска — читать логи** (стоячее правило проекта): ошибки
   разбираются сразу, а не после круга.

## Двойная бухгалтерия счётчиков

Все места, где одно и то же число живёт дважды. Сверяет `pegasgap doctor` (✅ Б1–Б4;
живая база: очередь 3960/48 = 3960/48, свод 2489 = 2489):

| Экран/API | База |
|---|---|
| «проверено N» в очереди | `count(cases where last_checked)` |
| «найдено M» в шапке | `count(problems)` по правилам findings (unique) |
| «разобрано K» | `count(gap_review)` пересечённый с открытыми проблемами |
| строки «держится N прогонов» | `gap_history.times_seen` |

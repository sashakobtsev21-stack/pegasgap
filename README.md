# pegasgap

Мониторинг пропусков туроператоров **Pegas Touristik**, **Coral Travel** и **Sunmar** на выдаче Слетать.

Инструмент отвечает на один вопрос: **где у оператора есть предложения на Турвизоре и
нет их у нас**. Турвизор здесь — эталон («что вообще есть на рынке»), Слетать —
проверяемая сторона. Найденные расхождения классифицируются по вероятной причине и
складываются в историю, чтобы было видно, какой пропуск появился сегодня, а какой висит
с прошлой недели.

Это не сравнение цен «кто дороже». Расхождение цены — лишь один из классов находок,
и не главный.

## Классы находок

| Класс | Что видно | Куда смотреть |
|---|---|---|
| **Туров нет совсем** | На Турвизоре предложения есть, на Слетать у оператора — ни одного | Плагин отработал и вернул пусто: направление/даты не заведены, фильтр отсёк всё. Сюда же попадает оператор, **отключённый на направлении** (`Enabled=false` в справочнике) |
| **Оператор не ответил** | Слетать: оператор в статусе «не отвечает» | Таймаут, бан, падение плагина — смотреть логи поиска, а не справочники |
| **Туров нет по отелю** | Отель есть на Турвизоре, у оператора на Слетать его нет | Разбирается по справочникам — см. ниже |
| **Цена расходится** | Отель есть на обеих, цена выбилась из обычного для прогона сдвига | Наценка, состав тура, курс |
| **Есть только у нас** | Есть на Слетать, нет на Турвизоре | Зеркало вопроса, по умолчанию скрыто: на живом обходе дало 587 строк из 641 и утопило настоящие находки. `PEGASGAP_REPORT_REVERSE=1` возвращает |

Названия говорят, ЧТО случилось, а не как это устроено внутри: «отельный пропуск» понятен
автору, а читателю отчёта нужно «туров нет».

Различие первых двух классов даёт статус оператора: шлюз отдаёт по каждому ТО `IsError`,
`IsTimeout` и `RowsCount`, то есть отдельно «отработал и вернул пусто» и «не ответил».
Корни у этих случаев разные, и смешивать их в одну кучу «нет цен» — значит отправлять
коллегу копать не туда.

## Разбор отельных пропусков по справочникам

«Этого отеля у нас нет» — это ещё не задача: непонятно, кто и что должен сделать.
Поэтому каждый отельный пропуск дополнительно разбирается по внутренним справочникам и
получает конкретный вердикт:

| Вердикт | Что установлено | Что делать |
|---|---|---|
| **нет в справочнике** | Отеля нет в каталоге Слетать вовсе | Завести отель |
| **нет линковки** | Отель в каталоге есть, но с каталогом оператора не связан | Связать |
| **линкован, тура нет** | Справочники в порядке | Смотреть наличие у оператора и логи поиска |
| **есть в справочнике** | Отель опознан, линковку проверить не удалось | Дать доступ к плагинной базе |
| **не опознан** | Похожий отель есть, но совпадение шаткое | Сверить название вручную |

Разбор двухуровневый, и второй уровень необязателен:

1. **Каталог отелей** — `GetHotels?countryId=<id>&all=-1` того же шлюза: полный список
   заведённых отелей страны (по Турции — 11 336). Работает без доступов. Отвечает,
   существует ли отель у нас вообще.
2. **Линковка оператора** — `SELECT` по таблице связей в плагинной базе оператора
   (имя базы задаётся переменной `PEGASGAP_PLUGIN_DB`, значения по умолчанию нет).
   Требует доступа к БД. Отвечает, связан ли отель с каталогом оператора.

Без второго уровня инструмент работает и даёт вердикт на ступень грубее — это
сознательно: молча выдать «нет линковки» там, где её просто не проверяли, значит
отправить человека править справочник, в котором всё в порядке.

Матчинг названий здесь тот же, что и для выдачи, — единый на весь инструмент. Иначе один
и тот же отель считался бы то тем же, то другим в зависимости от того, где его сравнивают.
На живых прогонах он вытягивает `SUNSTAR BEACH HOTEL` → `Sun Star Beach`,
`ALMERA PARK APARTMENT` → `Almera Park Apart Hotel`,
`DEXON ROMA HOTEL (EX. ROMA HOST WAY)` → `Dexon – Roma Hotel`.

## Установка

```bash
py -3.12 -m venv .venv
.venv\Scripts\python -m pip install -e ".[dev,browser,api,web,linking]"
.venv\Scripts\python -m playwright install chromium
cd frontend && npm install && npm run build && cd ..
```

Доступы не обязательны: обе площадки читаются анонимно. `.env` нужен только чтобы
включить проверку линковки в плагинной базе — см. «Разбор отельных пропусков».

## Интерфейс

```bash
.venv\Scripts\pegasgap web
```

Дашборд на `http://127.0.0.1:8000/` — три экрана:

* **Проверка** — отсюда всё запускается, двумя способами. *Регулярный обход* (открыт по
  умолчанию — это основной режим) проходит очередь из `scenarios.yaml`: собрать очередь,
  запустить, следить за счётчиками. *Одно направление* — форма под разбор конкретной
  жалобы: страна, город вылета, окно дат, ночи, режим, ответ сразу. Список операторов задаётся конфигом, а не выбирается на экране: обход
  идёт по всем сразу, и оператор — такое же измерение кейса, как город или дата.
* **Мониторинг** — отчёт, наполняется на ходу во время обхода; новые находки
  дописываются снизу. Управления здесь нет намеренно: экран, где вперемешку кнопки и
  находки, плохо делает и то и другое.
* **Логи** — живой поток событий обхода, с кнопкой очистки: лог за сутки обхода
  пролистать нельзя, а нужен он ровно про ту проверку, которую разбираешь сейчас.

Обход останавливается кнопкой в шапке — она видна с любого экрана и спрашивает
подтверждение. Останов не мгновенный: текущий кейс доводится до конца, иначе в базе
оседал бы прогон с половиной выдачи, который потом не отличить от настоящего недобора.

Отдельной «Истории» нет: возраст находки, перечень непроверенного и период переехали в
«Мониторинг». Возраст — главный признак, отделяющий устойчивую проблему от разовой ряби
выдачи, и держать его отдельно от решения, которое по нему принимают, было нелепо.

Что есть в отчёте:

* **Свод повторов.** Одна проблема — одна строка, даже если она встретилась в десятке
  прогонов; подпись говорит, чем варианты различаются: «8 случаев · различаются: 2 окна
  вылета · 7 и 10 ноч.». На живых данных 500 строк сворачиваются в 113. Раскрытие
  показывает каждый вариант.
* **Две ссылки** на тот же поиск — на Слетать и на Турвизоре, обе с оператором и
  конкретным отелем.
* **Цены сторон** в рублях с разницей, а не голые проценты.
* **Отметка «разобрано»** ставится на проблему целиком и переживает перепроверки
  направления.
* **Фильтры**: оператор, город вылета, страна, класс, причина. Значения берутся из самого
  отчёта, а не из конфига: иначе список предлагал бы срезы, по которым ничего нет.
* **Панель непроверенного** — прогоны, которым нельзя верить, с причинами. Прогон с
  проблемой это дыра в покрытии, и молчать о ней значит выдавать неполный отчёт за полный.

Обход идёт в фоне на сервере, поэтому закрытая вкладка его не прерывает.

Авторизации нет намеренно: инструмент внутренний, а данные в нём — публичная выдача двух
витрин. Экран входа тут не защищал бы ни от кого, зато добавил бы сессии и права, которые
надо поддерживать.

Всё то же доступно из командной строки — см. «Запуск» ниже; веб и CLI работают с одной
базой и одним `scenarios.yaml`.

## Какие направления мониторить

```bash
pegasgap top
```

Меряет, где у оператора реально есть предложения, и печатает готовый блок `routes:` для
`scenarios.yaml`. Автоматически не применяется намеренно: список направлений, который
меняется сам, — плохое свойство для мониторинга, потому что направление может тихо выпасть
из наблюдения и никто этого не заметит.

Мерить, а не брать флаг популярности площадки, приходится по делу: у Турвизора в
«популярных» лежат Китай и Куба, где у Pegas ровно ноль. Замер дешёвый — объём виден в
состоянии поиска, саму выдачу тянуть не нужно.

Два ограничения, которые стоит знать заранее:

* **Города вылета у площадок называются по-разному.** Турвизор сокращает
  («С.Петербург», «Н.Новгород», «Мин.Воды») — это разбирается алиасами в провайдере.
  Некоторых городов у него нет вовсе: Ростова-на-Дону, например. Прежде чем добавлять
  город в матрицу, стоит убедиться, что он есть в справочниках ОБЕИХ площадок, иначе
  кейс будет мёртвым.
* **Обе площадки считают запросы по IP.** Шлюз отвечает «превышен лимит кол-ва
  поисковых запросов», Турвизор — `HTTP 401 Invalid session`. Отсюда прокси (ниже) и
  пауза перед повтором.

### Прокси

Без них обход не проходит: на прямом адресе он встаёт на первом десятке кейсов, а с
постраничным сбором эталона — ещё раньше. Точечные проверки при этом продолжают работать,
так что отсутствие прокси выглядит обманчиво безобидно.

```bash
cp proxies.example.txt proxies.txt
```

Дальше вставьте список в `proxies.txt` — по одному в строке, в том же формате, в котором
их обычно выдают: `host:port:логин:пароль` (или `host:port` без авторизации). Файл в
`.gitignore`: там пары логин-пароль, а репозиторий публичный, и утёкшие оттуда креды не
отозвать — публичный гит сканируют боты.

Пул виден на «Проверке» и в `GET /api/proxies`; `POST /api/proxies/reload` перечитывает
файл без перезапуска сервера. Адреса наружу не отдаются, в логах прокси печатается как
`host:port` без кредов.

Прокси выдаётся **на весь поиск**, а не на запрос: постраничный сбор ходит по одному
`requestid`, и витрина связывает его с адресом — сменить IP на середине значит получить
чужую страницу. Засвеченный адрес (401/403/429/«превышен лимит») уходит остывать на
десять минут, а не выбрасывается: он не сломан, и выбрасывать его насовсем значило бы
за один обход сточить весь список.

### Из чего складывается очередь

Матрица — произведение семи измерений, и её размер полезно уметь считать в уме:

| измерение | откуда | сейчас |
|---|---|---|
| операторы | `operators:` | 3 |
| города вылета | `defaults.departure_cities:` | 10 |
| страны | `countries:` (или пары в `routes:`) | 10 |
| режимы | `modes:` — туры и отели | 2 |
| глубина продаж | `windows:` — смещение от дня запуска | 6 |
| длительность | `nights:` | 2 |
| состав туристов | `pax:` | 1 |

Туры: 3 × 10 × 10 × 6 × 2 = 3600. Отели: 3 × **1** × 10 × 6 × 2 = 360. Итого **3960**.

Города в режиме «отели» схлопываются в один намеренно: это проживание без перелёта, и
витрина подставляет там псевдогород «Без перелета» независимо от запроса. Десять городов
дали бы десять побайтово одинаковых поисков и десять копий одной находки — схлопывание
убирает 3240 пустых кейсов из 7200.

Три последних измерения существуют потому, что пропуск у оператора редко живёт «на
стране» целиком: неделя есть, а десяти ночей нет; ближние даты распроданы, а средняя
глубина пустая; двоим взрослым выдача идёт, а семье с ребёнком — нет. На одном значении
каждого измерения такие пропуски просто невидимы.

**Размер очереди не обязан совпадать с пропускной способностью.** Очередь — список работ,
упорядоченный по приоритету направления и давности проверки; воркер идёт по нему ровно с
той скоростью, которую терпят площадки, и сам останавливается после трёх подряд
несостоявшихся проверок. Большая матрица означает не перегрузку, а более длинный полный
круг: 420 кейсов при девяти секундах на кейс — около часа чистого времени, но упирается
всё в лимиты, а не в этот час.

Число стран упирается в то, что конфигом не лечится: из девятнадцати стран, где у
оператора есть предложения у нас, на витрине Турвизора он присутствует лишь в семи —
ОАЭ, Таиланд и Кипр туда не поставляются вовсе, и сравнивать там не с чем.

Города вылета когда-то держал такой же потолок: считалось, что шлюз игнорирует
`cityFromId` и любой город, кроме Москвы, вернёт московскую выдачу под чужой вывеской.
Это оказалось неверно — вывод был сделан по слишком грубому сравнению. Шлюз город
применяет: Москва 846 отелей, Петербург 780, Екатеринбург 770, Казань 649, Новосибирск
724 (Турция, одно окно, Pegas), отпечатки состава и цен у всех разные. Измерение городов
открыто, и матрица стоит на десяти.

Ловушка, на которой сгорел прежний вывод, никуда не делась, и попасться в неё легко
второй раз: **первая страница выдачи городов почти не различает**. Она отсортирована по
цене, а самые дешёвые туры у соседних городов совпадают — Екатеринбург и Казань дают на
ней побайтово одинаковые двести строк. Так же ведёт себя и счётчик `RowsCount` в
состоянии поиска: 272 и там, и там. Различие видно только на выдаче, забранной целиком.

## Запуск

Точечная проверка одного направления:

```bash
pegasgap scan --country Турция --from Москва --date-from 2026-09-10 --date-to 2026-09-20 --nights 7
```

Регулярный обход матрицы направлений из `scenarios.yaml`:

```bash
pegasgap sweep
```

Отчёт по накопленной истории:

```bash
pegasgap report --days 7
```

Разовая служебная команда — дозаполнить ссылки на витрину в прогонах, сделанных до того,
как эти ссылки появились:

```bash
pegasgap fill-links
```

## Как это устроено

Обе стороны опрашиваются **параллельно** — это не оптимизация, а требование
корректности: цены живые, и последовательный прогон сравнивал бы выдачи, снятые в разные
моменты.

### Источники данных

| Сторона | Основной путь | Запасной |
|---|---|---|
| Турвизор (эталон) | **JSON** `xml/modsearch.php` + `search3.tourvisor.ru/modresult.php`, выдача постранично | Playwright |
| Слетать (проверяемая) | **JSON-шлюз** `module.sletat.ru/Main.svc` | Playwright, `sletat.ru/b2b` |

Обе стороны читаются данными, а не браузером: прогон занимает секунды вместо минуты, и
ломаться от редизайна нечему. Переключатели — `PEGASGAP_TOURVISOR_SOURCE=web` и
`PEGASGAP_SLETAT_SOURCE=web`, чтобы при расследовании сверить запрос обоими путями.

Шлюз Слетать лучше браузера не только скоростью:

* **Статус оператора приходит фактом.** `GetLoadState` отдаёт по каждому ТО
  `IsProcessed`, `RowsCount`, `IsError`, `IsTimeout` — то самое различие «отработал и
  вернул пусто» против «не ответил». В браузерном пути его приходится вычитывать из
  подписей панели «блинчик».
* **Имя оператора есть в каждой строке выдачи.** Значит фильтр по ТО применяется
  достоверно, и главная угроза точности отчёта на этой стороне исчезает.
* Нечему протухнуть от редизайна.

Шлюз отвечает анонимно — нужен лишь заголовок `Referer`, поэтому он и стоит по умолчанию
независимо от наличия доступов. Логин и пароль поддержаны на случай, если шлюз когда-нибудь
потребует их для расширенной выдачи: значения читаются только из окружения, а URL уходит в
логи с вырезанными `login`/`password`.

> **Состояние браузерного пути к Слетать.** Он унаследован из проекта сравнения площадок
> и на текущей вёрстке b2b **не работает**: селектор выбора страны
> (`.slsf-country-to__select-text`) на живой странице не находится, поиск падает с
> «направление не предлагается» для любой страны. Чинить его имеет смысл только если
> понадобится сверять шлюз с тем, что реально видит агент в интерфейсе.

### Протокол Турвизора

Публичной документации у него нет, всё снято с живой страницы:

1. `xml/listdev.php?type=departure,allcountry,operator` — справочники: имя → id
   (Москва = 1, Турция = 4, Pegas Touristik = 12).
2. `xml/listdev.php?type=allhotel&hotcountry=<id>` — словарь отелей страны (~11 700
   записей). В выдаче поиска отели приходят **только идентификаторами**, имя берётся
   отсюда. Словарь весит около двух мегабайт и кешируется на процесс.
3. `xml/modsearch.php?...&operators=<id>` — запуск поиска: `requestid` + операторы со
   статусами. Фильтр по оператору серверный.
4. `search3.tourvisor.ru/modresult.php?requestid=<id>` — результат: блоки по операторам с
   отелями и ценами. Готовность — `data.status.finished`.

5. Следующая страница — повторный `modsearch.php` с `nextpage=1` и тем же `requestid`.
   Ответ **кумулятивен**: приходит вся выдача с начала, а не прирост.

Оба хоста требуют `referrer` **параметром запроса** и заголовок `Referer`, причём
указывающий на ту самую страницу, чью форму мы имитируем: с туровым реферером запрос в
режиме отелей отбивается 401.

### Ссылки на поиск

Каждая находка несёт ссылки на тот же поиск на обеих площадках — иначе её можно проверить
только повторив поиск руками по десятку полей формы.

**Слетать.** `/search/from-<город>-to-<страна>-for-<месяц>-nights-<a>..<b>-adults-N-kids-…`
плюс `datefrom`, `dateto`, `ticketsincluded`, `operators=<id ТО>`, `hotels=<id отеля>`.
Имена в пути английские, и составные пишутся через ПОДЧЁРКИВАНИЕ (`saint_petersburg`):
дефис у площадки разделяет поля пути, и на нём город молча теряется. Из параметров
фильтрации работает именно `operators` — не `f_to_id` (как в шлюзе) и не
`visibleOperators` (как в её же бандле).

**Турвизор.** `/tours/<страна>/<город>?ts_dosearch=1&s_form_mode=…&s_flyfrom=…&s_country=…`
плюс даты, ночи, туристы, `s_oplimit=<id ТО>`, `x_hotel_codes=<id отеля>`. Ключевой
параметр — `ts_dosearch=1`: без него страница показывает свои значения по умолчанию и всё
остальное игнорирует. Путь при этом лишь носитель: `s_country` и `s_flyfrom` перекрывают
его целиком, а страницы направления существуют не для всех стран (Грузии и России нет) —
там путь запасной, разойдётся только заголовок.

### Насколько полон эталон

Выдача витрины приходит **страницами примерно по полтора десятка отелей**, и её надо
забирать до конца. То, что на сайте выглядит кнопкой «показать ещё», — это повторный
вызов `modsearch.php` с `nextpage=1` и тем же `requestid`; у `modresult.php` параметра
страницы нет вовсе.

Долгое время это принимали за жёсткую обрезку на стороне площадки, и сравнение шло против
первой страницы: по Турции 15 отелей вместо 177, то есть **восемь процентов эталона** —
пропуск за пределами первой страницы обнаружить было физически нельзя.

Полностью собранной выдача считается, когда очередная страница не приносит новых отелей.
Упёрлись в `PEGASGAP_TOURVISOR_PAGES` (по умолчанию 10) раньше — результат помечается
`truncated`. Пустая выдача — тоже полная: листать нечего, и «у оператора здесь ничего
нет» это законный ответ, а не недобор. Пока это не различали, Абхазия с нулём отелей
шла как обрезанная.

Предел страниц — сознательный размен, и цену ему стоит знать. Замер по Турции (Москва,
Pegas): десять страниц дают 151 отель за ~30 с, тридцать — 436 отелей за ~111 с, и на
тридцати выдача всё ещё не кончилась. Полный круг очереди при этом растягивается втрое.
Пропусков за пределом страниц мы не видим, но и лишнего не выдумываем — обрезка эталона
теряет полноту, а не корректность (ниже).

Обрезка **эталона** ложных находок не даёт: отель, который мы увидели, мы увидели, и
пропуск по нему настоящий независимо от того, сколько осталось за кадром. Это потеря
полноты, а не корректности, поэтому она идёт заметкой. А вот обрезка **нашей** стороны —
проблема: недогруженный отель неотличим от отсутствующего.

Заметка (`notes`) и проблема (`problems`) разведены намеренно: первая описывает условия
сбора, вторая обесценивает находки, и прогон с ней недостоверен целиком.

### Цены

База у сторон разная (агентская против розничной), поэтому находкой считается не сама
разница, а **отклонение от обычного для прогона расхождения**. Ширина «обычного» берётся
из самих данных (медиана ± три медианных абсолютных отклонения): на живых прогонах разница
расползается на 4–13% при медиане около 9%, и фиксированный допуск объявлял бы выбросами
отели, где цена совпала до рубля.

Меньше трёх сопоставленных пар цену не сравниваем вовсе: при двух медиана совпадает с
наблюдением, и каждая пара оказывается выбросом относительно другой.

Систематический сдвиг свыше 25% означает, что стороны считают разное. Это **заметка, а
не брак прогона**: обесценивает она только находки по цене, а отельные пропуски остаются
в силе — отеля либо нет у оператора, либо он есть, и к тому, по какой базе считают цену,
это отношения не имеет. Прежде такой сдвиг бранил прогон целиком, и на живых данных 74
прогона утащили за собой 1834 честных отельных пропуска.

Природа у сдвига бывает двух видов, и вердикт их различает. Постоянная разница
**в рублях** — это одна составляющая тура, практически всегда перевозка: тур есть перелёт
плюс проживание, и перевозка одна на все отели. Замер по Грузии: 209262/134195,
212956/137888, 198182/123115 — разница 75067, 75068, 75067 на все двадцать семь пар.
Пропорциональная разница означает другое определение цены (состав тура, число туристов,
длительность).

Отличаем по разбросу: разница должна быть впятеро ровнее самих цен. Если цены отелей
между собой почти не различаются, вопрос неразрешим — постоянная в рублях и постоянная в
процентах совпадают, — и остаётся осторожная формулировка.

**Что сравнивается.** Минимум по окну берётся с каждой стороны независимо, и минимумы
легко приходятся на разные даты заезда. Поэтому находка помнит заезд, питание и номер
нашего предложения и показывает их строкой «наш минимум: заезд 23.10 · AI · Стандартный
номер» — иначе «расхождение −11.8%» читается как разница площадок, хотя это разница дат.

## Достоверность

Два места, где инструмент может соврать, и что с ними сделано:

**Фильтр по оператору.** Обе площадки фильтруют по ТО на своей стороне, и обе могут
фильтр не применить. На Турвизоре это опаснее: карточки отелей не несут имени оператора,
а в фильтре по умолчанию предотмечен промо-оператор, — если фильтр слетел, цена карточки
это минимум по всем ТО, и любой вывод о пропусках на таких данных ложный.

Поэтому фильтр проверяется **по самой выдаче, а не по факту отправки параметра**. На
Турвизоре — что все блоки ответа принадлежат нашему оператору. На Слетать — что имя
оператора в строках наше: шлюз кладёт его в каждую строку, и достаточно посчитать долю
(порог `MIN_OWN_ROWS_SHARE`, 90%; не 100% — единичная чужая строка встречается и брака не
заслуживает). Отправленный параметр говорит лишь о том, что мы попросили; доля своих
строк — о том, что получили. Непрошедший проверку прогон помечается недостоверным
(`problems`), а не молча идёт в отчёт.

**Те ли параметры искали.** Весь инструмент стоит на допущении, что обе площадки
выполнили ОДИН И ТОТ ЖЕ поиск, — и допущение это долго ничем не проверялось. Уйди
однажды в одну площадку двое взрослых, а в другую трое, отели всё равно сойдутся, и
отчёт спокойно покажет «пропуски», которых нет: концепция инструмента оказалась бы
фиктивной, а понять это по отчёту было бы нельзя.

Теперь параметры сверяются напрямую (`paramcheck.py`), и не по эху запроса, а по тому,
что о себе сообщают сами предложения: каждое несёт дату заезда, число ночей и оператора.
Если больше десятой части выдачи выпадает из запрошенного окна дат, диапазона ночей или
принадлежит чужому ТО — прогон недостоверен, а в причине указано, что просили и что
пришло. Пустая выдача расхождений не даёт: молчание здесь честнее выдуманной уверенности.

**Сопоставление отелей.** Ложный пропуск из-за расхождения названий — худший баг этого
инструмента: он создаёт работу на пустом месте. Поэтому матчинг намеренно **щедрый**, а
неуверенные случаи уходят в отдельную корзину «требует проверки» и в пропуски не
попадают. Пропустить реальный пропуск здесь дешевле, чем выдумать несуществующий.

**Несостоявшаяся проверка — не находка.** Если поиск на стороне Слетать упал, отвалился
по таймауту или площадка не приняла запрос, инструмент **молчит** и пишет причину в
`problems`. Пустая выдача из-за собственной поломки выглядит точь-в-точь как пропуск
оператора, и выдавать одно за другое — самый быстрый способ обесценить отчёт.

**Обрезанная выдача.** Отель, который не догрузился, неотличим от отсутствующего. Выдача
забирается до конца, а если упёрлись в предохранитель — прогон помечается недостоверным.

**Незавершённый поиск шлюза.** Опрос состояния идёт до готовности всех операторов, и по
таймауту шлюз раньше молча отдавал последнее состояние: строки тянулись из НЕЗАВЕРШЁННОГО
поиска и подавались как полная выдача. Цена ошибки — по Египту наша сторона вернула 42
отеля вместо 347, и девяносто пять отелей эталона стали «пропусками», которых нет. Теперь
незавершённый поиск помечает выдачу обрезанной, то есть бракует прогон.

**Развалившийся матчинг против настоящего пропуска.** Низкая доля сопоставленных отелей
двусмысленна: она одинаково выглядит и когда сломалась нормализация имён, и когда у
оператора действительно нет почти ничего из показанного эталоном. `detect` выбирает
осторожную версию, потому что справочника у него нет. А на стадии диагностики он есть, и
двусмысленность снимается: если 60% и больше пропущенных отелей уверенно опознаны в нашем
справочнике, значит имена читаются, и вердикт снимается. Опознание идёт ТЕМ ЖЕ матчером,
что и сопоставление выдач. Снимается ровно этот вердикт — прочие проблемы остаются.

**Отключённый оператор — находка, а не сбор.** Если в справочнике направления у оператора
стоит `Enabled=false`, поиск не выполняется вовсе: искать нечего, и это определённый факт,
а не неудача. Прогон достоверен и даёт полный пропуск с заметкой. Раньше такой случай
схлопывался в «фильтр не применился, данные непригодны», и по Мальдивам 64 прогона уходили
в мусор — при том что витрина показывает там 387 отелей Pegas.

## Разработка

```bash
.venv\Scripts\ruff check src/ tests/
```

```bash
.venv\Scripts\python -m pytest -q
```

Фронтенд (React + Vite + Tailwind, дизайн-система перенесена из проекта сравнения
площадок):

```bash
cd frontend && npm test && npm run build
```

Собранный `frontend/dist` раздаётся FastAPI под `/app` и в репозиторий не попадает —
после правок фронта пересоберите. Для разработки удобнее два процесса:
`pegasgap web` (бэкенд :8000) и `npm run dev` (фронт :5173 с проксированием `/api`).

Набор правил ruff зафиксирован явно в `pyproject.toml`: дефолтный набор линтера
расширяется от версии к версии, и гейт, завязанный на «то, что ruff считает дефолтом
сегодня», краснеет сам собой без единой правки в коде.

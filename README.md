# pegasgap

Мониторинг пропусков туроператоров **Pegas Touristik**, **Coral Travel** и **Sunmar** на выдаче Слетать.

Инструмент отвечает на один вопрос: **где у оператора есть предложения на Турвизоре и
нет их у нас**. Турвизор здесь — эталон («что вообще есть на рынке»), Слетать —
проверяемая сторона. Найденные расхождения классифицируются по вероятной причине и
складываются в историю, чтобы было видно, какой пропуск появился сегодня, а какой висит
с прошлой недели.

Это не сравнение цен «кто дороже». Расхождение цены — лишь один из классов находок,
и не главный.

## Классы находок

| Класс | Что видно | Куда смотреть |
|---|---|---|
| **Полный пропуск** | На Турвизоре предложения есть, на Слетать у оператора — ни одного | Плагин отработал и вернул пусто: направление/даты не заведены, фильтр отсёк всё |
| **Оператор не ответил** | Слетать: оператор в статусе «не отвечает» | Таймаут, бан, падение плагина — смотреть логи поиска, а не справочники |
| **Отельный пропуск** | Отель есть на Турвизоре, у оператора на Слетать его нет | Разбирается по справочникам — см. ниже |
| **Расхождение цены** | Отель есть на обеих, цены разошлись сверх порога | Наценка, состав тура, курс |
| **Обратный пропуск** | Есть на Слетать, нет на Турвизоре | Обычно шум эталона; если массово — проверить матчинг отелей |

Различие первых двух классов даёт статус оператора: шлюз отдаёт по каждому ТО `IsError`,
`IsTimeout` и `RowsCount`, то есть отдельно «отработал и вернул пусто» и «не ответил».
Корни у этих случаев разные, и смешивать их в одну кучу «нет цен» — значит отправлять
коллегу копать не туда.

## Разбор отельных пропусков по справочникам

«Этого отеля у нас нет» — это ещё не задача: непонятно, кто и что должен сделать.
Поэтому каждый отельный пропуск дополнительно разбирается по внутренним справочникам и
получает конкретный вердикт:

| Вердикт | Что установлено | Что делать |
|---|---|---|
| **нет в справочнике** | Отеля нет в каталоге Слетать вовсе | Завести отель |
| **нет линковки** | Отель в каталоге есть, но с каталогом оператора не связан | Связать |
| **линкован, тура нет** | Справочники в порядке | Смотреть наличие у оператора и логи поиска |
| **есть в справочнике** | Отель опознан, линковку проверить не удалось | Дать доступ к плагинной базе |
| **не опознан** | Похожий отель есть, но совпадение шаткое | Сверить название вручную |

Разбор двухуровневый, и второй уровень необязателен:

1. **Каталог отелей** — `GetHotels?countryId=<id>&all=-1` того же шлюза: полный список
   заведённых отелей страны (по Турции — 11 336). Работает без доступов. Отвечает,
   существует ли отель у нас вообще.
2. **Линковка оператора** — `SELECT` по таблице связей в плагинной базе оператора
   (имя базы задаётся переменной `PEGASGAP_PLUGIN_DB`, значения по умолчанию нет).
   Требует доступа к БД. Отвечает, связан ли отель с каталогом оператора.

Без второго уровня инструмент работает и даёт вердикт на ступень грубее — это
сознательно: молча выдать «нет линковки» там, где её просто не проверяли, значит
отправить человека править справочник, в котором всё в порядке.

Матчинг названий здесь тот же, что и для выдачи, — единый на весь инструмент. Иначе один
и тот же отель считался бы то тем же, то другим в зависимости от того, где его сравнивают.
На живых прогонах он вытягивает `SUNSTAR BEACH HOTEL` → `Sun Star Beach`,
`ALMERA PARK APARTMENT` → `Almera Park Apart Hotel`,
`DEXON ROMA HOTEL (EX. ROMA HOST WAY)` → `Dexon – Roma Hotel`.

## Установка

```bash
py -3.12 -m venv .venv
.venv\Scripts\python -m pip install -e ".[dev,browser,api,web,linking]"
.venv\Scripts\python -m playwright install chromium
cd frontend && npm install && npm run build && cd ..
```

Доступы не обязательны: обе площадки читаются анонимно. `.env` нужен только чтобы
включить проверку линковки в плагинной базе — см. «Разбор отельных пропусков».

## Интерфейс

```bash
.venv\Scripts\pegasgap web
```

Дашборд на `http://127.0.0.1:8000/` — четыре экрана:

* **Проверка** — отсюда всё запускается, двумя способами. *Одно направление* — форма
  под разбор конкретной жалобы: страна, город вылета, окно дат, ночи, режим, ответ сразу.
  *Полная по топу* — обход очереди из `scenarios.yaml`: собрать очередь, запустить, следить
  за счётчиками. Список операторов задаётся конфигом, а не выбирается на экране: обход
  идёт по всем сразу, и оператор — такое же измерение кейса, как город или дата.
* **Мониторинг** — только отчёт, наполняется на ходу во время обхода. Управления здесь
  нет намеренно: экран, где вперемешку кнопки и находки, плохо делает и то и другое.
* **Логи** — живой поток событий обхода.
* **История** — сводка находок за период, список прогонов и застарелые находки.

Обход идёт в фоне на сервере, поэтому закрытая вкладка его не прерывает.

Авторизации нет намеренно: инструмент внутренний, а данные в нём — публичная выдача двух
витрин. Экран входа тут не защищал бы ни от кого, зато добавил бы сессии и права, которые
надо поддерживать.

Всё то же доступно из командной строки — см. «Запуск» ниже; веб и CLI работают с одной
базой и одним `scenarios.yaml`.

## Какие направления мониторить

```bash
pegasgap top
```

Меряет, где у оператора реально есть предложения, и печатает готовый блок `routes:` для
`scenarios.yaml`. Автоматически не применяется намеренно: список направлений, который
меняется сам, — плохое свойство для мониторинга, потому что направление может тихо выпасть
из наблюдения и никто этого не заметит.

Мерить, а не брать флаг популярности площадки, приходится по делу: у Турвизора в
«популярных» лежат Китай и Куба, где у Pegas ровно ноль. Замер дешёвый — объём виден в
состоянии поиска, саму выдачу тянуть не нужно.

Два ограничения, которые стоит знать заранее:

* **Города вылета у площадок называются по-разному.** Турвизор сокращает
  («С.Петербург», «Н.Новгород», «Мин.Воды») — это разбирается алиасами в провайдере.
  Некоторых городов у него нет вовсе: Ростова-на-Дону, например. Прежде чем добавлять
  город в матрицу, стоит убедиться, что он есть в справочниках ОБЕИХ площадок, иначе
  кейс будет мёртвым.
* **Шлюз считает поиски по IP** и при превышении отвечает «превышен лимит кол-ва
  поисковых запросов». Отсюда невысокая параллельность замера и пауза перед повтором.

### Из чего складывается очередь

Матрица — произведение семи измерений, и её размер полезно уметь считать в уме:

| измерение | откуда | сейчас |
|---|---|---|
| операторы | `operators:` | 3 |
| города вылета | `defaults.departure_cities:` | 10 |
| страны | `countries:` (или пары в `routes:`) | 10 |
| режимы | `modes:` — туры и отели | 2 |
| глубина продаж | `windows:` — смещение от дня запуска | 6 |
| длительность | `nights:` | 2 |
| состав туристов | `pax:` | 1 |

Туры: 3 × 10 × 10 × 6 × 2 = 3600. Отели: 3 × **1** × 10 × 6 × 2 = 360. Итого **3960**.

Города в режиме «отели» схлопываются в один намеренно: это проживание без перелёта, и
витрина подставляет там псевдогород «Без перелета» независимо от запроса. Десять городов
дали бы десять побайтово одинаковых поисков и десять копий одной находки — схлопывание
убирает 3240 пустых кейсов из 7200.

Три последних измерения существуют потому, что пропуск у оператора редко живёт «на
стране» целиком: неделя есть, а десяти ночей нет; ближние даты распроданы, а средняя
глубина пустая; двоим взрослым выдача идёт, а семье с ребёнком — нет. На одном значении
каждого измерения такие пропуски просто невидимы.

**Размер очереди не обязан совпадать с пропускной способностью.** Очередь — список работ,
упорядоченный по приоритету направления и давности проверки; воркер идёт по нему ровно с
той скоростью, которую терпят площадки, и сам останавливается после трёх подряд
несостоявшихся проверок. Большая матрица означает не перегрузку, а более длинный полный
круг: 420 кейсов при девяти секундах на кейс — около часа чистого времени, но упирается
всё в лимиты, а не в этот час.

Число направлений упирается в две вещи, которые конфигом не лечатся. Из девятнадцати
стран, где у оператора есть предложения у нас, на витрине Турвизора он присутствует лишь
в семи — ОАЭ, Таиланд и Кипр туда не поставляются вовсе, и сравнивать там не с чем.
А города вылета держит `cityFromId` (см. выше): пока шлюз его игнорирует, любой город,
кроме Москвы, давал бы московскую выдачу под чужой вывеской.

## Запуск

Точечная проверка одного направления:

```bash
pegasgap scan --country Турция --from Москва --date-from 2026-09-10 --date-to 2026-09-20 --nights 7
```

Регулярный обход матрицы направлений из `scenarios.yaml`:

```bash
pegasgap sweep
```

Отчёт по накопленной истории:

```bash
pegasgap report --days 7
```

## Как это устроено

Обе стороны опрашиваются **параллельно** — это не оптимизация, а требование
корректности: цены живые, и последовательный прогон сравнивал бы выдачи, снятые в разные
моменты.

### Источники данных

| Сторона | Основной путь | Запасной |
|---|---|---|
| Турвизор (эталон) | **JSON** `xml/modsearch.php` + `search3.tourvisor.ru/modresult.php` | Playwright (и он же для режима «Отели») |
| Слетать (проверяемая) | **JSON-шлюз** `module.sletat.ru/Main.svc` | Playwright, `sletat.ru/b2b` |

Обе стороны читаются данными, а не браузером: прогон занимает секунды вместо минуты, и
ломаться от редизайна нечему. Переключатели — `PEGASGAP_TOURVISOR_SOURCE=web` и
`PEGASGAP_SLETAT_SOURCE=web`, чтобы при расследовании сверить запрос обоими путями.

Шлюз Слетать лучше браузера не только скоростью:

* **Статус оператора приходит фактом.** `GetLoadState` отдаёт по каждому ТО
  `IsProcessed`, `RowsCount`, `IsError`, `IsTimeout` — то самое различие «отработал и
  вернул пусто» против «не ответил». В браузерном пути его приходится вычитывать из
  подписей панели «блинчик».
* **Имя оператора есть в каждой строке выдачи.** Значит фильтр по ТО применяется
  достоверно, и главная угроза точности отчёта на этой стороне исчезает.
* Нечему протухнуть от редизайна.

Шлюз отвечает анонимно — нужен лишь заголовок `Referer`, поэтому он и стоит по умолчанию
независимо от наличия доступов. Логин и пароль поддержаны на случай, если шлюз когда-нибудь
потребует их для расширенной выдачи: значения читаются только из окружения, а URL уходит в
логи с вырезанными `login`/`password`.

> **Состояние браузерного пути к Слетать.** Он унаследован из проекта сравнения площадок
> и на текущей вёрстке b2b **не работает**: селектор выбора страны
> (`.slsf-country-to__select-text`) на живой странице не находится, поиск падает с
> «направление не предлагается» для любой страны. Чинить его имеет смысл только если
> понадобится сверять шлюз с тем, что реально видит агент в интерфейсе.

### Протокол Турвизора

Публичной документации у него нет, всё снято с живой страницы:

1. `xml/listdev.php?type=departure,allcountry,operator` — справочники: имя → id
   (Москва = 1, Турция = 4, Pegas Touristik = 12).
2. `xml/listdev.php?type=allhotel&hotcountry=<id>` — словарь отелей страны (~11 700
   записей). В выдаче поиска отели приходят **только идентификаторами**, имя берётся
   отсюда. Словарь весит около двух мегабайт и кешируется на процесс.
3. `xml/modsearch.php?...&operators=<id>` — запуск поиска: `requestid` + операторы со
   статусами. Фильтр по оператору серверный.
4. `search3.tourvisor.ru/modresult.php?requestid=<id>` — результат: блоки по операторам с
   отелями и ценами. Готовность — `data.status.finished`.

Оба хоста требуют `referrer` **параметром запроса** и заголовок `Referer`.

### Насколько полон эталон

Витрина показывает по оператору **выборку, а не весь каталог**: блоки обрезаны полусотней
отелей, и по Pegas на популярном направлении выходит полтора-два десятка против почти
тысячи на Слетать. Это устройство площадки, а не недосбор — кнопка «показать ещё» к этому
моменту уже исчезает, то есть витрина считает выдачу полной.

Практическое следствие: эталон отвечает на вопрос «что Турвизор показывает по этому
оператору», а не «что у оператора вообще есть». Прямое направление — отель есть на
витрине, а у нас нет — от этого не страдает и остаётся главным результатом. Обратные
пропуски при таком перекосе скрываются как заведомый шум, о чём прогон пишет заметкой.

Заметка (`notes`) и проблема (`problems`) — разные вещи и разведены намеренно: перекос не
ставит находки под сомнение, а вот недособранная выдача (`truncated`) ставит, потому что
недогруженный отель неотличим от отсутствующего.

Цена на стороне Слетать — агентская (кабинет/шлюз), на стороне Турвизора — розничная
витрина. База разная, поэтому находкой по цене считается не сама разница, а **отклонение
от обычного для прогона расхождения**.

Ширина «обычного» берётся из самих данных (медиана ± три медианных абсолютных
отклонения), а не из константы. На живых прогонах разница расползается на 4–13% при
медиане около 9% — при фиксированном допуске в находки попадали бы отели, где цена
совпала до рубля: формально они дальше всех от медианы, по сути ничем не примечательны.

## Достоверность

Два места, где инструмент может соврать, и что с ними сделано:

**Фильтр по оператору на Турвизоре.** Карточки отелей там не несут имени оператора, а в
фильтре по умолчанию предотмечен промо-оператор. Если фильтр не применился, цена
карточки — это минимум по всем ТО, и любой вывод о пропусках на таких данных ложный.
Поэтому после поиска фильтр **проверяется**, и непрошедший проверку прогон помечается как
недостоверный (`problems`), а не молча идёт в отчёт.

**Сопоставление отелей.** Ложный пропуск из-за расхождения названий — худший баг этого
инструмента: он создаёт работу на пустом месте. Поэтому матчинг намеренно **щедрый**, а
неуверенные случаи уходят в отдельную корзину «требует проверки» и в пропуски не
попадают. Пропустить реальный пропуск здесь дешевле, чем выдумать несуществующий.

**Несостоявшаяся проверка — не находка.** Если поиск на стороне Слетать упал, отвалился
по таймауту или площадка не приняла запрос, инструмент **молчит** и пишет причину в
`problems`. Пустая выдача из-за собственной поломки выглядит точь-в-точь как пропуск
оператора, и выдавать одно за другое — самый быстрый способ обесценить отчёт.

**Обрезанная выдача.** Отель, который не догрузился, неотличим от отсутствующего. Лента
доматывается до конца, а если упёрлись в предохранитель — прогон помечается
недостоверным, а не выдаёт хвост каталога за пропуски.

## Разработка

```bash
.venv\Scripts\ruff check src/ tests/
```

```bash
.venv\Scripts\python -m pytest -q
```

Фронтенд (React + Vite + Tailwind, дизайн-система перенесена из проекта сравнения
площадок):

```bash
cd frontend && npm test && npm run build
```

Собранный `frontend/dist` раздаётся FastAPI под `/app` и в репозиторий не попадает —
после правок фронта пересоберите. Для разработки удобнее два процесса:
`pegasgap web` (бэкенд :8000) и `npm run dev` (фронт :5173 с проксированием `/api`).

Набор правил ruff зафиксирован явно в `pyproject.toml`: дефолтный набор линтера
расширяется от версии к версии, и гейт, завязанный на «то, что ruff считает дефолтом
сегодня», краснеет сам собой без единой правки в коде.
